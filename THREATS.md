# THREATS.md - how TrustVault could be broken, and what stops it

**Scope.** The deployed web application, its API, its storage on disk and its audit trail.
**Assets.** Document content (most valuable), document names/metadata, who-has-access information, the audit trail, credentials and sessions, encryption keys.
**Attackers considered.**
A. an outsider with no account · B. a signed-in user trying to reach documents not shared with them (the judge) · C. a grantee trying to do more than their level allows · D. an ex-employee / revoked user, or someone whose access has run out · E. someone holding a forwarded share link · F. a malicious or compromised administrator · G. an insider with write access to the server's disk or database.

**How to read this file.** Each row: the attack → what was done → the test(s) that prove it (all in `tests/`) → what remains.
Every authorisation check named below is tagged `AUTHZ-CHECK[...]` in the code; `tools/mutation_check.py` removes each one in turn and confirms that a test fails.

Status legend: **Mitigated** (prevented and tested) · **Detected** (cannot be prevented by the app, but is recorded and alerted) · **Residual** (known gap, stated honestly).

## 2. Taking access away (attacker D) - "works immediately"

**What "immediately" means here:** the next HTTP request after the revocation commits is refused. There are no JWTs and no cached permissions: every request looks up the session, the user and the grant in the database. The one signed token we issue - a 5-minute share link - is checked against the document's `access_version` on every use, so revoking kills it at once too (T66).
**What it costs:** one indexed DB lookup per request (microseconds in SQLite); all file bytes must flow through the app (no CDN offload); horizontal scaling would need a shared database (see T51).

## 3. Share links (attacker E)

Phase 1 replaced the anonymous, long-lived external links with **signed links for one named person that work for
`LINK_TTL_SECONDS` (5 minutes)** - and only while that person **still holds a live grant**: a link never gives access
on its own, and can only narrow the grant's level. There is no anonymous document route any more.

| # | Threat | What we did | Proof | Status |
|---|---|---|---|---|
| T13 | **Guessing or forging a link**, or reading links from a DB copy. | A link is `v1.<claims>.<HMAC-SHA256>`; the key is derived from the master key (never in the DB) with its own label. Links are **not stored** at all - a DB copy holds none. A changed claim (level, expiry, recipient) breaks the signature (`link-signature-valid`); constant-time compare; per-user rate limit on opening. Bad signatures are audited (`link_invalid`) and alerted (`link_tampering`). | `test_links.py::test_tampered_or_made_up_links_are_refused` (upgrade view→download and +1 h → refused), `test_link_is_for_one_person_for_five_minutes` (token never in the audit row), `test_admin.py::test_alert_on_forwarded_and_tampered_links` | Mitigated / Detected |
| T14 | **Leaked / forwarded link** used by someone else, or for a long time. | The link names its recipient: it only works for that person, **signed in** as themselves (`link-bound-to-recipient`) - forwarded to anyone else, even an admin or someone with their own grant, it opens nothing (reason `wrong_user`) and raises a *forwarded_link* alert. The recipient must also still hold a live grant (`link-recipient-needs-grant` at creation; `no-permission-no-access` / `expired-grant-ignored` on every use). ## 7. The audit trail (attackers F, G) - "an audit trail that can be quietly altered is not evidence"

**What stops quiet alteration:** (1) SQLite triggers make `audit_log` append-only for the application; (2) each row's `entry_hash = HMAC-SHA256(audit_key, all fields + prev_hash)` - the key is **not in the database**, so someone who can edit the DB cannot forge a valid chain; (3) after every commit the newest `(seq, hash)` is appended to an anchor file **outside** the database, which catches deleting the newest rows (a chain alone cannot). `verify()` checks all three and the presence of the triggers.

| # | Threat | What we did | Proof | Status |
|---|---|---|---|---|
| T34 | Insider with DB write access **edits** (who/what), **deletes** a middle row, **re-orders** rows, **truncates** the tail, or **re-hashes** with plain SHA-256. | As above. Verification failure → **critical** alert on the admin dashboard with the first bad sequence number. | `test_audit.py`: `test_application_cannot_update_or_delete_audit_rows`, `test_edited_row_is_detected`, `test_rehashed_row_without_the_key_is_detected`, `test_deleted_middle_row_is_detected`, `test_truncated_tail_is_detected_by_external_anchor`, `test_reordered_rows_are_detected`; `scripts/tamper_demo.py` | Detected |

## How the tests prove the checks matter

```
python tools/mutation_check.py
```

removes each of the 71 tagged checks one at a time and runs the whole suite against each mutant. The hand-in run killed **every** mutant (see `tools/mutation_check.py --list` for each check and its mutation). If you add a check, tag it; if the tool reports a survivor, a test is missing.
